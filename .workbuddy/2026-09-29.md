## 教训（已踩）

远程命令里 `ls` 一个 750 权限、属主是别人的目录会返回非零；在 `set -e` 脚本里这会静默中止后续步骤，而且因为 stdout 缓冲，前面的成功输出也可能看不到。**排查时不要用 `set -e`，或对预期可能失败的 `ls` 显式加 `|| true`。**

## 用户裁定（2026-09-29 第二轮）与 Phase 5 前置

**三项指令，已落地：**

## 两个必须记住的坑（已写入技能）

1. **绝不在远程命令里用 heredoc。** `cat >> file <<YAML` 会被**本地** shim 解析执行（报 `providers:: command not found`），服务器只收到 6 行被改写过的注释，真正的键没写进去。恢复方式：从 `backups/config.yaml.bak-before-phase5` 回滚，然后改用**本地写文件 → scp → `sed -i 's/\r$//'` → `cat >>` → 删片段**，一次成功。多行 `python3 -c "..."` 同样会被弄坏。

## ⚠️ 我上一轮写错了一个结论，已纠正

我在 §11.16 说"`_entry_matches` 是精确匹配、**没有通配符**可用"——**这是错的**。我读的是基类 `access_policy_mixin.py:45-46` 的 `return target in entries`，**没注意到 QQ 适配器覆盖了它**（`qqbot/adapter.py:1669-1671`）：

```python
def _entry_matches(self, entries, target):
    normalized_target = str(target).strip().lower()
    return any(str(e).strip().lower() in ("*", normalized_target) for e in entries)
```

**它支持 `"*"`，且大小写不敏感。** 也就是说本来用 `group_allow_from: ["*"]` 就能抓 openid，**那次临时 `group_policy: open` 窗口本来不必要**（也就不需要动启动守护和 `QQ_ALLOW_ALL_USERS`）。已在文档里保留原错误文本并标注纠正，因为这处错误直接导致了一个更重的决定。

**安全推论**：`"*"` 等于"全开"——写在 `group_allow_from` 就是机器人所在的所有群，写在 `allow_from` 就是所有私聊发送者。**必须把 `"*"` 当作 allow-all 开关看待，不是便利写法。**

## 记忆与身份架构查证（回答"能否按人长期记忆 / 能否辨别用户 / 能否联合群与私聊"）

- **按人长期记忆：不存在。** 内置 store 是**全实例一份**的一对文件，路径里没有 user/session 组件：`tools/memory_tool.py:38-40 get_memory_dir() -> get_hermes_home()/"memories"`；`memory_tool_store.py:212` 目的地只有 `USER.md`/`MEMORY.md`；工具 `target` 枚举是 `user|memory`（单数语义）。`~/.hermes/memories/` **目前是空的，从未写入过**。多用户共用 → 跟 A 聊出的条目会注入 B 的 prompt，**结构性串味**。
  - 唯一实例级隔离原语是 **profile**（`profiles.py` 的 `_PROFILE_DIRS` 含 `memories`/`sessions`），但 profile = 一路 bot/一个实例，**网关没有把终端用户路由到 profile 的机制**，不能拿它做按人记忆。
  - 外部 provider（honcho/openviking/mem0/holographic/retaindb/byterover/supermemory）已装插件未启用，部分有 per-user namespace，但 **AGENTS.md §11 禁止 V1 上**。
- **辨别用户：能，但模型只拿到裸 openid。** 会话键 `agent:main:qqbot:dm:<user_openid>` / `agent:main:qqbot:group:<group_openid>:<user_openid>`（`session.py:673 build_session_key()`），`config.yaml` 显式 `group_sessions_per_user: true`，`sessions` 表 7 行数据正确。
  - **QQ Bot API v2 不传昵称**——适配器只读 `author.user_openid`/`member_openid`，线上无 name 字段。**机器人不可能知道任何人名字**，人格里"称呼自由发挥"是被迫的。
  - 模型看到 `## Current Session Context` 的 `**Source:** Qqbot (DM with <openid>)`（`session.py:375` 构建，`run_agent_cache.py:629` 调用，确认在网关回合路径上）；`privacy.redact_pii=false` → **裸 openid**。
  - **群里 `[昵称]` 前缀不会加**：`run_inbound.py:1413` 仅在 `is_shared_multi_user_session()` 为真时加，而 `group_sessions_per_user: true` 时返回 False（`session.py:633-641`）。**副作用：机器人实际上不参与群聊**——每个成员各自会话，看不到其他人说了什么。想让机器人跟整个群上下文走需把它改 `false`（代价：全群共用一个会话、互相可见）。
- **群与私聊联合：三层三种答案。** ① 对话上下文**有意不联合**（不同会话键，AGENTS.md §10 要求）；② 长期记忆**被动全联合**（全局文件、任何聊写入都注入所有聊、**无归属字段**）；③ `session_search` **联合且无作用域**——搜索路径不带 user/chat 过滤，`current_session_id` **只用于排除当前活跃会话**（`session_search_tool.py:355-414`、`_list_recent_sessions:480-499`），全机共用一个 `state.db`。

  - **规矩已立**：把任何用户/群加入白名单前，先裁定 `session_search` 是否保留在消息平台上。
- **身份连续性**：同一 `user_openid` 同时出现在 dm 键与群键里 → "某人跨私聊+群"在基础设施层可关联，但当前无任何机制去做。
